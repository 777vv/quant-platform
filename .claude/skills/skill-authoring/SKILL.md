# 技能编写规范（skill-authoring）

> 官方最佳实践（意图 → 草稿 → 2-3 个真实测试提示 → 看结果 → 迭代）见插件技能 `skill-creator`；
> **本技能只补"本项目怎么落地"**，两者互补，不要重复抄写。

## 1. 先判断：这份知识该放哪一层（放错层是最大的浪费）

| 内容性质 | 放这里 | 加载时机 |
| --- | --- | --- |
| 每次会话都得记得的**规则与索引**（铁律、命令、约定） | `AGENTS.md` | 每次会话自动注入 |
| 某类任务反复要用、**按需触发**的流程与领域知识 | 技能 `SKILL.md` | 描述命中时才加载 |
| 需要推导、有修订历史的**细节与权威口径** | `docs/02-技术文档.md`（人类权威） | 由人/模型主动查阅 |
| 与"人怎么用这个系统"有关的说明 | `README.md` | 由人查阅 |

- 判断口诀：**"每次都要"→ 记忆；"做这类事才要"→ 技能；"要查证"→ 文档。**
- 同一件事**只在一处维护**：技能里需要细节时，用一句引用指向 `docs/02` 或另一个技能，不要粘贴正文（两边会漂移）。

## 2. 目录与 frontmatter（硬性规则）

```text
.zcode/skills/<技能名>/
├── SKILL.md          # 必需
├── scripts/          # 可选：可复用的脚本（避免每次让模型重写）
├── references/       # 可选：按需读取的长文档
└── assets/           # 可选：模板/样例
```

必需的两项 frontmatter：

- `name`：小写 kebab-case（1–64 字符），**必须与目录名一致**；不要与已有技能重名（尤其插件技能，如 `skill-creator`、`frontend-ui`）。
- `description`：**既是"做什么"也是"何时触发"**——模型倾向于**少触发**，所以要写得稍微"主动"：包含动作、适用场景与触发词。
  - ✅ 好例：`本项目里创建或修改「技能」时必须先读的编写规范……触发词：创建 skill、写 SKILL.md、技能规范。`
  - ✗ 差例：`技能编写规范`（没说什么场景该用，模型不会触发）。

**只使用 `name` + `description` 两个字段**：本项目技能要在 ZCode 与 Claude Code 两处各存一份镜像，而两工具对其它字段（`allowed-tools`、`model`、`context` 等）支持不一致；一旦引入工具专有字段，镜像就无法逐字节一致、同步脚本会失效。确有需要时，先与用户确认是否接受"镜像不再等同"的代价。

## 3. 正文怎么写（结合本项目）

- **语言**：本项目全部文件与注释用中文（用户要求）；方法/字段的注释与备注要求同 `AGENTS.md` 第 2 条。
- **渐进披露**：`SKILL.md` 控制在 **500 行以内**，能一句话说清的不要写三段；细节挪到 `references/` 并在正文写明"何时去读它"。
- **可执行优先**：给出具体命令与路径（`sh sync-memory.sh --write`），比"记得同步"这种口号有用。
- **解释为什么**：规则不显然时补一句原因（例：为什么镜像是必要的——两工具技能目录不能共用），比全大写 MUST/NEVER 更有效。
- **正反例对照**：涉及格式或写法时给一小段 ✅/✗ 示例。
- **不要与 `AGENTS.md` 重复**：技能里若需要某条铁律，写"见 AGENTS.md 第 N 条"，不要复制。

## 4. 落地清单（创建/修改技能后逐项走完）

1. 目录名 = frontmatter `name`，kebab-case，且不与现有技能重名（先 `ls .zcode/skills`）。
2. `description` 里写了"何时用 + 触发词"，并读一遍自问：**换个说法提问还能命中吗**。
3. 内容按第 1 节判断过层级，没有把"每次都要的规则"藏进技能、也没把"细节正文"抄进技能。
4. 需要脚本/模板时放进该技能的 `scripts/`、`assets/`，正文给出调用方式。
5. **同步两处镜像（必须）**：`sh sync-memory.sh --write` 生成 `.claude/skills/` 镜像，再 `sh sync-memory.sh` 校验通过。
6. **登记文档（必须）**：`docs/02-技术文档.md` 加一条修订说明（沿用 ①②③… 编号）；`docs/03-任务清单.md` 追加迭代行。
7. 若该技能改变了"人怎么用项目"的行为，同步更新 `README.md` 的技能清单那一节。
8. 修改**已有**技能时保持 `name` 与目录名不变；不要另起 `xxx-v2`。

## 5. 验证（别只看"文件写好了"）

- 机械校验：`sh sync-memory.sh` 会检查两份镜像逐字节一致、frontmatter 有 `name`/`description`、`name` 与目录名一致。
- 行为校验：用一条**真实口吻的测试提示**（包含具体路径/口语化措辞）在新会话里试一次，看它会不会被加载、结论是否正确；若模型被技能带着做无用功（反复读同一文件、绕圈），说明写得太啰嗦——**减字比加规则有效**。

## 6. 反面清单（本项目踩过/见过的）

- ✗ 技能里复制粘贴 `AGENTS.md` 或 `docs/02` 的正文 → 两处维护必然漂移。
- ✗ `description` 只写名词不写场景 → 永远不触发。
- ✗ 为"更保险"堆叠一堆 MUST/NEVER → 模型把注意力花在规则上，正事反而做差。
- ✗ 只写进 `.zcode/skills/` 就收工 → Claude Code 侧读不到（忘记镜像同步）。
- ✗ 把"每次会话都要记得的规则"塞进技能 → 技能是**按需**加载的，平时根本不会进上下文。
